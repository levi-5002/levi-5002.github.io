Windows x64 异常处理之 VEH：从 CPU 异常、进程级处理器链、系统调用顺序到 x64dbg 与 ML64 实验

一、VEH 是什么：为什么已有 SEH 还需要 VEH？

1. 先区分异常、调试器、SEH 和 VEH

异常不是程序立即崩溃。例如：

或者主动产生一个容易控制的可继续软件异常：

Windows 会描述异常并保存故障线程上下文，然后按相应分发路径寻找能处理异常的代码。

VEH（Vectored Exception Handling，向量化异常处理） 是 Windows 提供的进程级异常回调机制。程序通过 AddVectoredExceptionHandler 将一个函数加入当前进程的异常处理器列表；当异常真正到达程序的用户态异常分发时，系统可以先调用这些回调，再搜索普通的栈帧式 SEH。

“向量化”在这里是 Windows 对此处理器机制的名称，不意味着使用了 CPU 的 SIMD/XMM/YMM 向量指令，也不是 CPU IDT 中断向量表。

2. VEH 与 SEH 的根本区别

比较项 VEH SEH（__try/__except）
注册方式 AddVectoredExceptionHandler MSVC 编译器扩展 __try/__except

与栈帧绑定 否 是
处理器如何定位 根据进程中已注册的回调链 根据 RIP、活动栈帧、函数表与语言作用域数据
常规执行时机 调试器首次机会之后，栈帧 SEH 搜索之前 VEH 未接管后参与搜索
回调参数 EXCEPTION_POINTERS*（一个参数） C Filter 的表达式；底层语言处理器有四个参数

常见应用 异常观察、日志采集、特定故障现场恢复 局部错误恢复、受保护作用域处理及 __finally 清理

例如线程 A 与 B 都执行 Fault()，VEH 可以在两个线程的异常中执行同一段回调代码，而不同线程的 SEH 仍然按照各自的活动栈帧寻找。

VEH 的进程级含义不是“在一个专门的异常线程中运行”。回调通常仍然由产生异常的那个线程执行。使用 GetCurrentThreadId() 可以在回调中获取该线程的 ID。

3. VEH、VCH、顶层 UEF 不要混淆

缩写 名称 代表 API 主要使用时机
VEH Vectored Exception Handler AddVectoredExceptionHandler 分发早期观察或处理异常
VCH Vectored Continue Handler AddVectoredContinueHandler 与异常恢复/继续相关的后续阶段，和 VEH 是不同列表
SEH Structured Exception Handling __try/__except 当前线程的栈帧式异常搜索
UEF Unhandled Exception Filter SetUnhandledExceptionFilter 异常到达顶层未处理路径时可能调用

正常的 VEH 处理成功后，无须再调用普通 SEH 执行相同异常的处理块；普通 SEH 已处理异常后，也不应推断顶层 UEF 一定执行。

4. 两个非常容易忽略的资源管理问题

第一：同一回调可以被注册多次。 注册返回的多个句柄分别代表注册项，可能导致同一函数在一次异常分发中被多次调用。不要重复注册却只注销其中一个。

第二：回调在 DLL 内时，卸载 DLL 前必须注销。 Microsoft 的 API 文档明确指出：即使包含回调代码的 DLL 已被卸载，注册项仍可保留；之后再次触发异常，就可能间接调用一个已无效的地址。

此外，VEH 可能与其他线程并发执行。生产代码还需设计注册、注销与线程退出时的生存期协调，避免回调仍在运行期间释放其依赖的数据。不要把 VEH 当成可随意执行大量 I/O、锁操作、内存分配的普通日志回调。

六、PEB 与 VEH 向量异常处理机制

1.PEB 与 VEH 有什么关系？

PEB（Process Environment Block，进程环境块）是 Windows 为每个进程维护的一种用户态数据结构，包含进程加载器、进程堆、调试状态以及部分运行时状态信息。

VEH（Vectored Exception Handling，向量异常处理）是一种进程级异常处理机制。与基于栈帧的 SEH 不同，VEH 允许程序注册全局异常回调函数，在异常分发过程中提前检查或处理异常。

需要注意的是：PEB 并不直接保存 VEH 异常处理器链表，也不直接保存每个 VEH 回调函数的地址。

PEB 通过 CrossProcessFlags 字段中的特定位，记录进程是否正在使用 VEH 或 VCH 机制。而真正的 VEH/VCH 注册信息则由 ntdll.dll 内部的数据结构维护。

八、VEH 返回值：什么时候继续搜索，什么时候恢复现场？

1. VEH 的正常返回值只有两种

回调返回 含义 下一步
EXCEPTION_CONTINUE_SEARCH (0) 此 VEH 不接管异常 继续遍历后续 VEH；均未接管则进入 SEH 搜索
EXCEPTION_CONTINUE_EXECUTION (-1) 当前异常已被处理，请尝试恢复上下文 结束后续异常搜索，按适用路径进入 VCH/上下文恢复

不要在 VEH 回调中使用 EXCEPTION_EXECUTE_HANDLER (1) 作为“已处理”返回值。

因为 VEH 不依赖某一个 __try。开发者可以预先注册回调，然后在不同函数中故意触发异常，使用保存的 CONTEXT 决定后续执行位置。

这种模式可以出现在合法的异常恢复、兼容性工具、调试和程序分析中，也可能被反调试/控制流混淆程序利用。不能仅仅因为某程序注册了 VEH 就认定其恶意。

2. 为什么直接 NOP 掉故意异常可能仍然失败？

如果异常回调还承担初始化、状态变更或特定控制流转移，NOP 掉故意异常指令可能绕过必要步骤，造成后续程序行为异常。

逆向时更适合先判断：

  • 哪个异常代码被目标 VEH 关注？
  • VEH 在什么地址调用？
  • 它修改了哪些 CONTEXT 字段？
  • EXCEPTION_CONTINUE_SEARCH 和 EXCEPTION_CONTINUE_EXECUTION 哪条路径被选中？
  • 同一异常是否可能被其他 VEH、SEH 进一步接管？

3. 为什么调试器可能让 VEH 看不到异常？

因为调试器的首次处理机会在目标程序自己的 VEH 之前。如果调试器把某个异常声明为已处理，VEH 可能完全得不到机会。

对 int3、单步等调试相关异常尤其应区分调试器自身设置的事件与程序故意产生的事件。使用 x64dbg 时，可以分别测试“传递异常”和“吞掉异常”的效果，而不是直接把所有异常代码配置为忽略。

4. 线程、进程与异常传播边界

AddVectoredExceptionHandler 的注册范围是当前进程；它不会自动成为其他独立进程的异常处理器。

同一进程中不同线程共享此回调注册，但不会共享一个正在抛出异常的线程的寄存器上下文。一个线程的 __try 也不会自动捕获另一个线程的异常。

VEH 回调 LONG 0（**EXCEPTION_CONTINUE_SEARCH**）： 当前 VEH 不处理异常，继续调用后续 VEH；如果都不处理，再进入普通 SEH 搜索。-1（**EXCEPTION_CONTINUE_EXECUTION**）： 当前 VEH 请求恢复异常执行，停止正常的后续 VEH 搜索，系统尝试使用保存或修改后的 CONTEXT 恢复线程。1 不是 VEH 正常的处理返回值。
VCH 回调 LONG 0（**EXCEPTION_CONTINUE_SEARCH**）： 在典型实现中，当前 VCH 不停止列表遍历，继续调用下一个 VCH；并不意味着重新进入 SEH。-1（**EXCEPTION_CONTINUE_EXECUTION**）： 可使后续 VCH 停止执行。VCH 主要参与继续执行阶段，其返回值通常不会推翻之前 VEH/SEH 已经作出的恢复决定。具体遍历行为需结合 Windows 版本。
RtlpCallVectoredHandlers 内部协议 某些 Windows 版本通过它遍历 VEH/VCH 列表并检查回调结果。如果某个 VEH 返回 -1 请求恢复，该内部函数可能向上层返回表示已处理的状态，例如 1；如果没有处理器接管，则报告未处理状态。其内部返回值不一定等于 VEH 原始返回值，具体协议不属于稳定公开接口。
RtlLookupFunctionEntry PRUNTIME_FUNCTION 非 NULL： 找到当前 ControlPc 所属的运行时函数表项，返回 RUNTIME_FUNCTION*，用于定位 .pdata/.xdata 中的展开信息。NULL： 没有找到对应表项，系统可能按叶函数规则继续虚拟展开；不代表异常已经处理失败。
RtlVirtualUnwind PEXCEPTION_ROUTINE 非 NULL： 返回当前栈帧适用的底层语言处理器地址，例如 __C_specific_handler。NULL： 没有适用的语言处理器，但仍可能成功计算调用者上下文。无论是否返回处理器，都会按照展开规则更新提供的 CONTEXT，并通过输出参数提供相关数据。
RtlpxVirtualUnwind 内部协议 Windows 某些版本使用的内部虚拟展开函数，可能通过 EAX=0 表示本次展开操作成功，其他状态表示特定情况或失败，并通过输出参数提供语言处理器和栈帧信息。它的 0 不等于 SEH 的 **ExceptionContinueExecution**；实际必须根据当前 Windows 版本的反汇编判断。
RtlpExecuteHandlerForException 内部协议 用于调用当前栈帧关联的语言异常处理器。正常返回时，通常可将处理器的 EXCEPTION_DISPOSITION 结果交回异常分发器，例如 0=请求继续执行，1=继续搜索。但如果语言处理器直接启动栈展开，可能不会正常返回。具体包装器协议属于内部实现。
__C_specific_handler EXCEPTION_DISPOSITION 0（**ExceptionContinueExecution**）： 当前语言处理器请求恢复异常执行。1（**ExceptionContinueSearch**）： 当前处理器不接管，继续寻找其他作用域或外层栈帧。2（**ExceptionNestedException**）： 与嵌套异常分发有关。3（**ExceptionCollidedUnwind**）： 与展开过程中的重叠展开有关。如果 C Filter 选择执行 __except，它也可能直接调用 RtlUnwindEx，而不是正常返回。
C **__except** Filter LONG -1（**EXCEPTION_CONTINUE_EXECUTION**）： 请求恢复异常发生时的执行上下文。0（**EXCEPTION_CONTINUE_SEARCH**）： 当前作用域不处理，继续搜索。1（**EXCEPTION_EXECUTE_HANDLER**）： 选择执行当前 __except 处理块，必要时先进行栈展开。注意：它返回的 1 与 **__C_specific_handler** 返回的 1 含义完全不同。
RtlUnwindEx VOID 没有普通返回值。 它负责真正展开栈帧，退出不再需要的调用作用域，执行适用的 __finally，并将控制流转向目标处理位置。成功的非局部展开通常不会返回原调用点。没有 __finally 也可能需要调用它。
RtlDispatchException BOOLEAN TRUE（1）： 本次用户态异常分发已经找到能够恢复执行的处理结果，外层可以进入恢复 CONTEXT 的路径。FALSE（0）： 本次分发没有解决异常，需要继续未处理异常处置。注意：如果语言处理器启动了非局部栈展开，也不一定通过普通的函数返回路径得到这个布尔值。
SetUnhandledExceptionFilter 函数指针 返回之前设置的顶层异常过滤器指针，供调用者保存。NULL： 通常表示此前没有设置顶层过滤器，不能据此认定这次注册失败。它本身返回的不是 -1/0/1 异常处理结果。
顶层异常过滤器回调 LONG -1： 尝试从异常现场恢复执行，需要异常可继续且上下文有效。0： 不接管，继续系统默认的顶层未处理异常流程。1： 选择外围未处理异常处理逻辑，通常最终终止进程，而不是直接恢复原来的业务代码。
UnhandledExceptionFilter LONG 0（**EXCEPTION_CONTINUE_SEARCH**）： 继续默认的未处理异常处置，例如进程正在被调试时交给调试器。1（**EXCEPTION_EXECUTE_HANDLER**）： 由关联的外围处理块执行最终处理，通常终止进程。-1（**EXCEPTION_CONTINUE_EXECUTION**）： 在允许的情况下请求恢复执行。它还可能根据条件调用用户通过 SetUnhandledExceptionFilter 注册的回调。
KiUserExceptionDispatcher 内部入口 不按普通函数返回值判断异常是否已处理。 它接收用户态异常现场，调用 RtlDispatchException。如果分发成功，进入恢复 CONTEXT 的路径；如果没有处理成功，可能通过 NtRaiseException 等接口继续向系统报告异常。
RtlRestoreContext VOID 没有普通返回值。 它根据传入的 CONTEXT 恢复线程的 RIP、RSP 和其他寄存器，并完成相应的非局部控制转移。成功恢复后，CPU 通常从目标 RIP 执行，而不是回到调用它的下一条指令。
NtContinue NTSTATUS 成功： 恢复指定的线程上下文，通常不再返回原来的调用位置，而是在目标 RIP 继续执行。失败： 可能返回对应的 NTSTATUS 错误状态。这里的状态码属于 NTSTATUS 协议，不能与异常过滤器的 -1/0/1 混淆。

特别需要注意的返回值区别：

  • VEH 返回 -1：请求恢复执行。
  • C __except Filter 返回 1：选择进入对应 __except。
  • __C_specific_handler 返回 1：继续搜索异常处理器。
  • RtlDispatchException 返回 1：整个异常分发已成功处理。
  • UnhandledExceptionFilter 返回 1：进入外围的最终异常处理路径，通常导致进程终止。

同一个数字在不同函数中有不同含义。逆向调试时必须先确定当前函数的返回值类型，再判断调用者怎样使用这个结果。

十六、结语：真正理解 VEH 的三个关键问题

第一，VEH 是怎么注册和找到的？

AddVectoredExceptionHandler 将回调加入进程级列表；异常到达用户态分发时，RtlDispatchException 的相关路径有机会按列表顺序调用它。它不需要先查询某个函数的 SCOPE_TABLE_AMD64 才能找到回调。

第二，VEH 拿到了什么？

回调接收一个 EXCEPTION_POINTERS*，里面有 EXCEPTION_RECORD* 和 CONTEXT*。它可以检查异常代码、发生位置及保存的寄存器状态，并在符合条件时修改现场，请求恢复执行。

第三，VEH 与其他异常处理层怎样衔接？

如果 VEH 返回 CONTINUE_SEARCH，会继续向后续 VEH 或普通栈帧 SEH 搜索；如果返回 CONTINUE_EXECUTION，系统会尝试恢复上下文，可能涉及 VCH。调试器首次机会位于这些用户处理器之前；顶层未处理过滤器是另一种最终处置机制，不能认为每次都会运行。

把本文的 C 程序的 chain / resume 两种模式，与上一篇原生 MASM SEH 的 PROC FRAME:SEH_Handler 实验进行对照，你就能在 x64dbg 中直接理解：同一个 ud2 故障现场，为什么既可以通过函数表式 SEH 找到处理器，也可以通过进程级 VEH 列表找到回调，但它们的函数原型和返回协议完全不同。
