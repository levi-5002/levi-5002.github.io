Socket 初探,跟踪 TCP 通信

​ 在分析网络程序时，只看函数调用，很难判断数据究竟传到了哪一步；只看抓包，又容易把协议栈行为误认为应用程序行为。这次实验将两种视角结合起来：用 x64dbg 观察 Winsock API 的参数、缓冲区和返回值，用 Wireshark 观察同一条 TCP 连接的握手、数据传输和关闭过程。

​ 实验包含一个服务端 server.exe 和一个客户端 client.exe。服务端监听 127.0.0.1:5566，客户端连接后发送请求，服务端处理并返回响应，最后双方关闭连接。沿着这条调用链，可以把 Socket 描述符、地址结构、字节序和 TCP 序列号联系起来。

1 实验环境与调试方法

1.1 通信流程

本文分析 Windows x64 下的 IPv4 TCP 通信，以阻塞式 Socket 的常规调用为主。双方运行在同一台计算机上，流量经过回环接口。

阶段 服务端 客户端
初始化 WSAStartup() WSAStartup()
创建套接字 socket() socket()
准备连接 bind()、listen() 准备服务端地址
建立连接 协议栈响应握手，accept() 取得连接 connect() 发起连接
交换数据 recv() 接收请求，send() 发送响应 send() 发送请求，recv() 接收响应
释放套接字 关闭通信 Socket 和监听 Socket 关闭客户端 Socket
清理环境 WSACleanup() WSACleanup()

accept() 可以先进入等待，也可以在连接已进入等待队列后调用。表中的流程描述各接口的职责，不意味着握手一定要等待服务端执行到 accept()。

实验截图来自数次调试，Socket 数值和内存地址可能变化。后文分别用 listenSocket、peerSocket、clientSocket 表示服务端监听 Socket、服务端通信 Socket 和客户端 Socket；具体数值只用于解释对应截图。

1.2 从 ws2_32.dll 定位网络调用

在 x64dbg 的模块列表中，可以看到 ws2_32.dll。它提供本文使用的 Winsock API，是追踪网络行为的入口。

其他模块可以帮助理解程序的运行环境：ucrtbase.dll 提供通用 C 运行库，kernel32.dll 和 kernelbase.dll 提供 Win32 基础功能，ntdll.dll 提供用户态 Native API。bcrypt.dll 与 Windows 密码学接口有关，但仅凭模块被加载，不能确定程序使用了哪种加密算法。

在符号列表中搜索 WSAStartup 时，可能同时看到“符号”和“导出”记录。

导出记录来自 DLL 对外公开的接口；符号名称则可能来自调试信息，既可以表示函数，也可以表示变量或其他对象。截图中两条 WSAStartup 记录的地址相同，指向同一入口。其他名称中含有 WSAStartup 的条目，不应直接当作该 API 的实现。

1.3 Windows x64 下如何读取参数

本文涉及的接口使用 Windows x64 调用约定。前四个整数或指针参数依次放在 RCX、RDX、R8、R9 中，但读取宽度应以函数原型为准。相关规则见微软的 x64 调用约定。

参数位置或返回类型 观察位置 例子
第一个参数 RCX 或其低位部分 SOCKET 读 RCX，int 读 ECX，WORD 读 CX
第二个参数 RDX 或其低位部分 指针读 RDX，int 读 EDX
第三个参数 R8 或其低位部分 指针读 R8，int 读 R8D
第四个参数 R9 或其低位部分 int flags 读 R9D
int 返回值 EAX 状态码、实际收发字节数
SOCKET 返回值 RAX x64 下的套接字描述符

调试器可能显示多于实际参数数量的寄存器或栈槽，不能把它们全部当作函数参数。这些参数寄存器也可能在函数内部被改写，因此查看返回后的缓冲区时，应使用入口处记下的地址，不能默认返回时的 RDX 仍然指向原缓冲区。

2 初始化 Winsock 并创建 Socket

2.1 WSAStartup 初始化进程的 Winsock 环境

wVersionRequested 指定应用程序支持的最高 Winsock 版本；lpWSAData 是指向 WSADATA 的输出指针，用于接收协商后的版本等信息。WSAAPI 是调用约定宏，本文的 x64 程序按前述 x64 规则传参。

两个参数分别回答“希望使用哪个版本”和“把初始化结果写到哪里”。其中 WORD 是 16 位无符号整数，LPWSADATA 是 WSADATA * 的类型别名，调用方需要提供一块可写的结构体存储空间。

版本参数 十六进制值 表示的 Winsock 版本
MAKEWORD(2, 2) 0x0202 2.2，本实验的选择
MAKEWORD(2, 1) 0x0102 2.1
MAKEWORD(2, 0) 0x0002 2.0
MAKEWORD(1, 1) 0x0101 1.1，旧程序中可能出现

这里选择的是 Winsock 接口版本，不是 IPv4 或 IPv6，也不是 TCP 版本。地址族和传输协议由后续的 socket() 参数指定。

RDX 保存 wsaData 的地址。函数调用前，那里只是准备接收输出的存储空间；成功返回后，再按 WSADATA 的字段解释内容。EAX=0 表示初始化成功，实际协商版本还可通过 wsaData.wVersion 检查。

Winsock 2 程序不应使用旧字段 iMaxSockets 判断可创建的 Socket 数量。结构体保存初始化信息，后续 bind()、send() 等操作使用的是各自的 Socket 描述符，不需要反复传入 wsaData。字段定义见 WSADATA 官方说明。

WSAStartup() 的错误处理有一个特殊点：失败时直接返回错误码，应读取该返回值，无需再调用 WSAGetLastError()。参见 WSAStartup 官方说明。

2.2 socket 创建 IPv4 TCP 套接字

先拆开这个声明：最前面的 SOCKET 是返回值类型，WSAAPI 描述调用约定，socket 是函数名，括号中的三个 int 分别选择地址族、套接字类型和具体协议。WSAAPI 不是需要传入的第四个参数；在 32 位 Windows 中通常对应 __stdcall，本文 x64 程序仍按前述寄存器规则调用。

af 决定使用什么地址体系。 对 IPv4、IPv6 程序，常见选择如下。表中数值采用 Windows SDK 定义，不应直接套用其他操作系统的数值。

常量 Windows 数值 含义 对后续调用的影响
AF_INET 2 IPv4 bind()、connect() 通常配合 sockaddr_in，如 127.0.0.1
AF_INET6 23 IPv6 配合 sockaddr_in6，本机回环地址为 ::1
AF_UNSPEC 0 未指定地址族 常见于地址解析的筛选条件，不宜作为此处明确创建 IPv4 或 IPv6 Socket 的选择

例如，程序可以先让 getaddrinfo() 使用 AF_UNSPEC 查询 IPv4 和 IPv6 候选地址，再把某个结果中的实际地址族传给 socket()。这与把 AF_UNSPEC 直接交给 socket() 是两个步骤。参见微软的客户端 Socket 创建示例。

type 决定数据以什么方式交付给应用程序。

常量 数值 通信方式 后续使用特点
SOCK_STREAM 1 有序、可靠、双向的字节流 常见于 TCP；连接建立后收发，应用自行划分消息边界
SOCK_DGRAM 2 数据报 常见于 UDP；保留数据报边界，但不保证送达或顺序
SOCK_RAW 3 原始套接字 用于特定协议的底层处理，受协议支持及系统权限限制，不是普通 TCP 收发接口

protocol 进一步指定实现这种通信的协议。

常见值 数值 典型组合
IPPROTO_TCP 6 AF_INET 或 AF_INET6 加 SOCK_STREAM
IPPROTO_UDP 17 AF_INET 或 AF_INET6 加 SOCK_DGRAM
0 0 由服务提供程序按前两个参数选择协议；常见 IP 流式组合选 TCP，数据报组合选 UDP

三个参数共同约束创建结果，不能任意拼接。例如，不能期待 SOCK_STREAM 搭配 IPPROTO_UDP 就得到“可靠 UDP”。不受支持的组合会创建失败。参数和可支持组合见 socket 官方说明。

下面几种写法的差别可以直接对应到后续流程：

TCP 服务端通常继续执行 bind → listen → accept，TCP 客户端执行 connect；UDP 常用 sendto() 指定本次目标、用 recvfrom() 接收并取得来源地址，不执行 TCP 的监听、接受连接和三次握手。UDP 也可以调用 connect() 关联默认对端，但这不会把 UDP 变成 TCP。有关无连接 Socket 上的含义，见 connect 官方说明。

参数 寄存器中的值 常量 含义
af ECX=2 AF_INET IPv4 地址族
type EDX=1 SOCK_STREAM 流式套接字

截图中返回值为 0x120。Windows 的 SOCKET 是指针宽度的无符号整数类型，在 x64 下占 8 字节，用于引用系统管理的套接字资源。它不是可以直接解引用的内存指针，也不是端口号。

socket() 失败时返回 INVALID_SOCKET，在 x64 下为 0xFFFFFFFFFFFFFFFF。因此，这里要检查完整的 RAX，不能沿用“返回 0 就成功”的判断方法。创建成功后，程序还需要继续绑定地址、建立连接；单独调用 socket() 并不会完成 TCP 握手。

后续 API 传入描述符时，系统会找到创建时选定的地址族、协议及当前连接状态。例如，send(s, ...) 不需要再次传入 AF_INET 和 IPPROTO_TCP。关闭成功后，s 变量里的数值不会自动清零，但它已经不能继续用于该 Socket。

2.3 阻塞模式与错误返回

SOCK_STREAM、SOCK_DGRAM 不负责选择阻塞或非阻塞模式。新建 Socket 默认阻塞，常见的切换接口是：

s 指定要设置的 Socket，cmd=FIONBIO 表示切换 I/O 模式，argp 指向一个 u_long 变量：值为 0 表示阻塞，非零表示非阻塞。这里传入的是变量地址，不是直接把 1 当作第三个参数。成功返回 0，失败返回 SOCKET_ERROR。参见 ioctlsocket 官方说明。

3 服务端绑定地址并开始监听

3.1 bind 关联本地地址

bind() 将套接字与本地地址关联。对于本次 IPv4 实验，第二个参数指向 sockaddr_in，第三个参数为结构体长度 16。函数成功返回 0，失败返回 SOCKET_ERROR，即整数 -1。参见 bind 官方说明。

参数 输入含义 常见写法与后续用途
s 已创建、尚未绑定的 Socket 描述符 使用 socket() 的成功返回值；绑定后继续传给 listen() 或收发相关接口
name 指向本地地址结构的只读指针 IPv4 通常传 (const struct sockaddr *)&addr；系统读取地址族、IP 和端口
namelen 地址结构占用的字节数 使用 sizeof(addr)；IPv4 的 sockaddr_in 为 16 字节

sockaddr 是通用接口形式，实际布局取决于地址族。把 sockaddr_in * 转成 sockaddr * 只是调整指针类型，不会把 IPv4 地址转换为 IPv6。若 addr 本身是指针，sizeof(addr) 得到的将是指针大小，不能代替它所指向的结构体长度。

截图中的 RCX=0x120 对应刚刚创建的 Socket，RDX 指向地址结构，R8D=0x10，即十进制的 16。

跟随 RDX 到内存窗口，可以看到结构体起始的 16 字节：

偏移 字段 大小 本次内存字节 含义
0x00 sin_family 2 字节 02 00 AF_INET=2
0x02 sin_port 2 字节 15 BE 端口 5566
0x04 sin_addr 4 字节 7F 00 00 01 地址 127.0.0.1
0x08 sin_zero 8 字节 全 0 保留字段

这里不能用一种字节序解释整个结构体。sin_family 使用主机字节序，Windows x64 下数值 2 存为 02 00；端口和 IPv4 地址使用网络字节序，即大端序。结构要求见 SOCKADDR_IN 官方说明。

实际编程时，本地地址和端口还有几种常见选择：

字段取值 含义 对后续通信的影响
IPv4 地址 127.0.0.1 绑定本机回环地址 本例只接受通过本机回环路径到达的连接
IPv4 地址 0.0.0.0，即 INADDR_ANY 不限定某一个本地 IPv4 地址 用于监听时可覆盖本机适用的 IPv4 地址，实际可达性仍取决于网络与系统配置
某个具体本机 IP 绑定指定的本地地址 适用于多网卡等需要明确选择地址的场景
端口 5566 等非零值 请求指定的本地端口 客户端需要连接这个端口
端口 0 请求系统分配可用端口 成功后通过 getsockname() 查询实际端口，再告知需要连接的一方

INADDR_ANY 是本地绑定的通配地址，不应当作为 connect() 的远端服务器地址。端口为 0 的分配方式也不表示服务真的在“0 号端口”上通信。相关规则见 bind 的地址选择说明。

绑定失败时，常见原因包括 WSAEADDRINUSE（地址或端口已被占用）和 WSAEADDRNOTAVAIL（指定的地址不是当前可用的本地地址）。先检查错误码，再决定修正地址、端口或程序的重复启动问题。

3.2 listen 使套接字进入监听状态

s 必须是已经绑定、尚未建立连接且支持监听的 Socket。本例传入 IPv4 TCP Socket；UDP 不使用这个监听流程。backlog 是一个整数配置值，常见写法如下：

backlog 写法 表达的请求
1 请求较小的待接受连接队列，本实验采用此值
16、128 等正整数 请求相应规模的待接受连接队列，具体值由应用选择
SOMAXCONN 让底层服务提供程序选择合理的最大队列规模

Windows SDK 中 SOMAXCONN 的数值为 0x7FFFFFFF，但它是一个特殊约定，不表示系统必然允许排队二十多亿个连接。

本次调用为 listen(listenSocket, 1)。其中 RCX 仍然是监听 Socket，EDX=1 是请求的待接受连接队列长度。

backlog 管理等待应用程序接受的连接，不表示服务器一生只能接受一个客户端，也不等于已经接受的连接总数上限。应用程序通过 accept() 取走一个连接后，可以继续接受其他连接；实际队列容量还受底层服务提供程序约束。参见 listen 官方说明。

listen() 成功返回 0 后，服务端具备了接受连接的条件。此时还没有客户端发起连接，Wireshark 中没有对应的握手报文是正常现象：监听是本地状态变化，并不主动向某个客户端发送 SYN。

之后应把同一个监听描述符传给 accept()。如果没有先绑定，可能得到 WSAEINVAL；若 Socket 类型不支持监听，则可能得到 WSAEOPNOTSUPP。listen() 返回的是操作状态，不会返回一个新的 Socket。

4 客户端连接与服务端接受连接

4.1 connect 指定远端地址

客户端同样先调用 WSAStartup() 和 socket()，随后调用：

connect() 和 bind() 的参数形式相似，但地址的含义不同：bind() 指定自己的本地地址，connect() 指定要连接的远端地址。

参数 本例应传入什么 成功后如何使用
s 客户端创建的 TCP Socket 后续仍使用同一个描述符调用 send()、recv()
name 指向服务端 127.0.0.1:5566 的地址结构 系统由此确定远端端点
namelen 对应地址结构的大小 IPv4 传 sizeof(struct sockaddr_in)，IPv6 使用对应的 IPv6 结构大小

name 虽然叫“名称”，但这里不是域名字符串。若目标是域名，通常先通过 getaddrinfo() 得到候选地址结构，再选择匹配的地址族创建 Socket 并尝试连接。

截图中地址结构的前 16 字节仍然表示 127.0.0.1:5566。客户端不需要提前显式调用 bind()：如果 Socket 尚未绑定，系统会在连接过程中隐式关联本地地址，并选择可用的临时端口。这仍然是绑定，只是由系统完成。阻塞模式下，connect() 返回 0 表示连接成功。参见 connect 官方说明。

需要区分两种返回情形：阻塞连接失败时，WSAECONNREFUSED 表示连接请求被拒绝，WSAETIMEDOUT 表示连接尝试超时；非阻塞连接返回 SOCKET_ERROR 且错误码为 WSAEWOULDBLOCK 时，通常表示连接正在进行。后者需要等待连接完成通知或相应的就绪事件，并检查最终结果，不能立即当作已经连接，也不应反复调用 connect() 代替完成检查。

与服务端的 accept() 不同，connect() 成功后不会产生需要从返回值接收的新描述符：客户端仍然使用传入的 s。

5.1 长度头确定消息边界

本实验的请求和响应都使用“4 字节长度头 + 载荷”的格式。长度头以大端序保存后续载荷的字节数，不包含长度头自身。

实验程序的请求载荷为 DES 密文，响应载荷为 AES 密文。网络分析关注的是这些载荷的边界与字节数；具体算法应通过程序的加解密逻辑识别，不能仅凭载荷长度或看起来不规则的字节判断。

5.2 TCP 不会自动转换应用数据的字节序

TCP/IP 首部中的多字节字段采用协议规定的网络字节序，但应用载荷如何编码，由应用协议决定。send() 按缓冲区中的字节顺序发送，recv() 交付收到的字节，不会自动把其中的整数换成大端或小端。

以 Windows x64 上的 32 位长度 8 为例：

状态 变量按本机整数查看 内存中的字节顺序
主机序整数 8 0x00000008 08 00 00 00
经 htonl(8) 转换后 0x08000000 00 00 00 08
接收上述网络序字节后，尚未转换 0x08000000 00 00 00 08
经 ntohl() 转换后 0x00000008 08 00 00 00

发送端可用 htonl() 编码长度，接收端在读满四字节后用 ntohl() 解码。转换的是整数在本机内存中的表示，send() 看到的仍然只是四个字节。有关转换宽度和网络序定义，参见 htonl 官方说明。

它们接收整数值并返回转换后的整数值，不接收待修改缓冲区的指针。h 表示 host，n 表示 network；名字中的 s 和 l 在这些接口中对应 16 位与 32 位，并不意味着 x64 下的 htonl() 会转换 64 位整数。

密文则应按加密接口产出的字节顺序传输，不应为了“网络大端序”把密文整体反转。

5.3 TCP 字节流与应用层消息不同

TCP 向应用程序提供有序字节流，不保留每次 send() 的调用边界。客户端可以分两次提交长度头和载荷，但服务端不一定恰好分两次收到。

即使接收端准备读四字节长度头，也可能先拿到 2 字节，再拿到 2 字节；后续读取必须移动写入位置，并把请求长度缩小为剩余字节数。反过来，如果接收端给出足够大的缓冲区，也可能在一次读取中拿到长度头和部分或全部载荷。

6 跟踪 send 与 recv 的实际行为

6.1 send 返回的是字节数

对于本例 TCP 通信，s 应当是已经建立连接的 Socket：客户端使用 connect() 成功后的描述符，服务端使用 accept() 返回的描述符，不能把监听 Socket 当作数据连接来发送。

buf 指向至少有 len 字节可读内容的内存。const char * 表示 API 从这里读取字节，不通过这个参数修改数据；它不要求内容是字符串。缓冲区可以保存文本、长度头或包含 00 的密文。

len 的单位是字节，不是字符数，也不是缓冲区内某个整数的数值。例如 send(s, "hello", 5, 0) 请求发送五字节，不包含字符串末尾的 \0。本例的密文和二进制长度头可能含零字节，不能用 strlen() 推断它们的长度。长度应由应用协议或加密接口的实际输出确定。

flags 是本次调用的选项，常见值如下：

flags Windows 数值 作用
0 0 普通发送，本实验采用此值
MSG_OOB 0x1 在支持的流式 Socket 上发送带外数据，普通业务消息通常不用
MSG_DONTROUTE 0x4 请求不使用常规路由查找；服务提供程序可以忽略此请求

这些标志属于 Winsock API 的调用选项，不是 TCP 首部中的 SYN、ACK、PSH 标志。flags=0 也不表示阻塞模式；阻塞与否是 Socket 的工作模式。选项及返回语义见 send 官方说明。

第一次发送时，参数可以解释为：

参数 截图中的值或位置 含义
s RCX=0x11C 客户端的已连接 Socket
buf RDX 指向发送缓冲区 本次数据的起始地址
len R8D=4 请求发送 4 字节
flags R9D=0 普通发送选项

这里的 0x11C 属于客户端进程。即使它与其他截图中的服务端描述符数值相同，也不代表同一个 Socket；描述符必须结合进程和本次运行理解。

RDX 指向的前四字节是 00 00 00 08。后面的内存虽然也能在 Dump 中看到，但 len=4 已经限定了本次请求发送的范围，不能把相邻内存一起算进本次数据。

函数的返回值为 EAX=4，表示这次有 4 字节被本地传输系统接受发送。send() 的成功返回不能证明对端程序已经调用 recv()，也不能证明对端已完成业务处理。返回的字节数还可能小于请求长度，发送逻辑应依据实际返回值处理剩余数据。参见 send 官方说明。

若请求发送 12 字节但只返回 5，下一次应从 buf+5 开始提交剩余 7 字节，不能从原缓冲区开头重发而造成重复数据。返回 SOCKET_ERROR 时先读取错误码；对于非阻塞 Socket，WSAEWOULDBLOCK 表示目前无法继续提交，需要等待可写机会。请求长度为 0 时允许成功返回 0，这与 recv() 返回 0 表示 TCP 接收方向结束的语义不同。

6.3 recv 将数据写入缓冲区

与 send() 相比，recv() 的 buf 不带 const，因为系统要向它指向的内存写入数据。调用方负责提供有效、可写且容量至少为 len 的缓冲区；len 是本次最多允许写入的字节数，实际写入量由返回值给出。

普通接收不会自动追加字符串结束符 \0。如果接收的是文本，应用需要在预留空间内自行终止字符串，或始终按返回长度处理；如果接收的是密文，就应当把它当作二进制字节序列。

flags Windows 数值 对本次接收的影响
0 0 普通读取，已读取的数据从接收队列中取走
MSG_PEEK 0x2 把数据复制到缓冲区，但不从接收队列中取走；后续普通读取仍可读到这些字节
MSG_OOB 0x1 读取支持的带外数据
MSG_WAITALL 0x8 在支持它的阻塞式流 Socket 上，请求等到缓冲区读满，或连接结束、取消、出错后返回

MSG_WAITALL 不能保证连接出错时仍然返回完整长度；它也不适用于非阻塞或数据报 Socket，且不能与 MSG_PEEK、MSG_OOB 等不兼容选项组合。返回值仍需检查。具体限制见 recv 的 flags 说明。

7 关闭连接并清理 Winsock

7.1 closesocket 释放指定套接字

这个接口只有一个参数，x64 下通过 RCX 传入要关闭的 Socket，成功返回 EAX=0，失败返回 SOCKET_ERROR。

s 可以是已经创建但尚未连接的 Socket、监听 Socket，或已连接的通信 Socket。关闭哪个资源，取决于传入哪个描述符；关闭服务端的监听 Socket 不会代替应用关闭所有已经接受的客户端 Socket。

Windows 的 Socket 应通过 closesocket() 释放，不应当因为描述符是整数就改用普通文件的关闭方式。一次成功关闭之后，可以把应用中的变量设为 INVALID_SOCKET，帮助后续代码识别“这个变量当前不再持有有效 Socket”。该赋值只是维护应用状态，并不会再执行一次系统关闭操作。

服务端在本次实验中先关闭与客户端通信的 peerSocket，再关闭监听用的 listenSocket。客户端则关闭自己的 clientSocket。已经关闭的描述符不能继续使用，系统也可能在之后重新分配同一个数值。

默认情况下，closesocket() 可以先返回，再由协议栈在后台继续正常关闭连接。因此，返回 0 并不等于四次挥手已经完成。关闭行为也受 SO_LINGER 等选项影响，某些配置会导致连接复位。参见 closesocket 官方说明。

closesocket() 本身没有“等待几秒”的参数。需要改变相关行为时，使用 setsockopt() 设置 SO_LINGER，其中 linger 结构包含 l_onoff 和 l_linger：

设置 典型行为
l_onoff=0 默认方式，关闭调用可立即返回，正常关闭过程在后台继续
l_onoff!=0、l_linger=0 中止式关闭，TCP 连接复位，不能用它保证剩余数据送达
l_onoff!=0、l_linger>0 对阻塞 Socket 等待待发送数据发出或等待超时；超时单位为秒

第三种配置也不能证明对端业务处理成功。非阻塞 Socket 启用非零 linger 超时时，关闭调用还可能以 WSAEWOULDBLOCK 失败，不能把所有关闭尝试都直接记为“资源已经释放”。

监听 Socket 本身不代表与某个客户端建立的双向数据连接，关闭它不会为“监听关系”单独产生一轮四次挥手。已经被 accept() 返回的通信 Socket 是另一个资源，仍需要单独管理。

顺序 报文编号 方向 标志 Seq Ack
1 125968 5566 → 46490 FIN, ACK 37 13
2 125969 46490 → 5566 ACK 13 38
3 126191 46490 → 5566 FIN, ACK 13 38
4 126192 5566 → 46490 ACK 38 14

服务端首先发送 FIN，表示它的发送方向结束。其 Seq=37 与之前发送的 36 字节应用数据对应；客户端回复 Ack=38，因为 FIN 与 SYN 一样，占用一个序列号。

客户端随后也发送 FIN，序列号为 13；服务端回复 Ack=14，确认客户端方向的结束。这与客户端此前发送 12 字节应用数据的结果一致。ACK、数据和 FIN 对序列号的影响，应分别计算。相关定义见 RFC 9293。

TCP 的两个方向分别关闭。客户端收到服务端 FIN 后，在自己的发送方向尚未关闭、且应用仍保留 Socket 时，协议层面仍允许它继续发送数据；服务端是否还能由应用接收这些数据，要看服务端调用的是半关闭接口还是已经释放了整个 Socket。不能仅凭一条 FIN 报文判断应用层还保留哪些资源。

本次服务端先发 FIN，并在确认客户端 FIN 后，按典型状态转换进入 TIME_WAIT；客户端收到服务端 FIN 后、应用关闭前，通常处于 CLOSE_WAIT。这些是 TCP 连接状态，不能与 closesocket() 是否已经返回简单画等号。

“四次挥手”描述两个方向分别结束并得到确认的过程，并不要求每次抓包都恰好出现四条独立报文。ACK 与 FIN 可以合并发送，重传也可能增加报文数量；本次记录恰好完整展示了四条报文。正常关闭和半关闭的协议行为见 RFC 9293 的连接关闭章节。

7.3 两个 FIN 之间的间隔

本次服务端发送 FIN 的时间约为 3833.8061178 s，客户端发送 FIN 的时间约为 3844.4262688 s，两者相差约 10.62 s。

这不是 TCP 要求的固定等待时间。实验正在对两个进程进行断点调试，客户端可能仍处于暂停状态，也可能尚未执行到关闭逻辑。抓包只能证明两次发送之间的间隔，具体原因需要结合对应线程的执行状态判断。

7.4 shutdown 控制连接的发送与接收方向

closesocket() 释放描述符，而 shutdown() 用于停止指定方向的操作：

s 指定要处理的 Socket；对本文 TCP 场景，应使用已连接的通信 Socket。how 选择停止哪个方向，通过 EDX 传入。成功返回 0，失败返回 SOCKET_ERROR。

how 数值 含义 后续影响
SD_RECEIVE 0 停止接收操作 不能继续对该 Socket 调用普通接收；不是发送 FIN 的替代方式
SD_SEND 1 停止发送操作 不能再发送新数据，仍可接收对端数据；TCP 随发送方向结束而发送 FIN
SD_BOTH 2 同时停止收发 两个方向均不再允许操作，但仍须释放 Socket

这些值是三个独立选项，不能把 SD_BOTH 理解为 SD_RECEIVE | SD_SEND 的计算结果。在 TCP 上关闭接收方向时，若还有未读数据或后续数据到达，可能触发连接复位，因此 SD_BOTH 不等于“更完整地保证正常关闭”。规则见 shutdown 官方说明。

shutdown(s, SD_SEND) 常用于表达“本端请求已经发送完，但还要继续接收响应”。它不会释放描述符，已经关闭的方向也不能靠另一次 shutdown() 重新打开。后续仍需按协议完成接收，再调用 closesocket()。

7.5 WSACleanup 与初始化次数对应

WSACleanup() 没有参数，成功返回 0，失败返回 SOCKET_ERROR。所以，即使断下时 RCX、RDX 等寄存器里还有数值，也不应把它们解释为该函数的参数。

每次成功的 WSAStartup() 都需要一次对应的 WSACleanup()。如果同一进程成功初始化两次，前一次清理只是减少引用计数，最后一次才执行实际清理。客户端和服务端是两个进程，各自维护自己的 Winsock 使用状态。参见 WSACleanup 官方说明。

这个计数与 Socket 数量无关：进程成功初始化一次后，即使创建了十个 Socket，也应分别关闭这十个资源，再为那一次初始化调用一次 WSACleanup()，而不是因为有十个 Socket 就清理十次。若某次 WSAStartup() 失败，它没有增加一次成功初始化，也不应为这次失败额外配对清理。

Winsock 的最终清理会影响该进程中其他线程的网络操作。因此，它通常处于应用或网络组件的整体生命周期末尾，而不是放在每一次 send()、recv() 或每一条连接结束后无条件执行。

需要明确控制正常结束过程时，可以在完成待发送数据后调用 shutdown(s, SD_SEND)，表示本端不再发送；接着按协议继续接收，直到对端正常结束，再调用 closesocket() 释放描述符，最后进行 Winsock 清理。shutdown() 本身不释放 Socket，也不能替代 closesocket()。具体时序应由双方协议约定，参见微软的正常关闭与套接字释放说明。

最终的 WSACleanup() 会清理进程中的 Winsock 操作和资源；如果还有尚未发送完的数据，过早清理可能影响这些数据，具体行为见 WSACleanup 的清理说明。因此，结束 API 调用、完成协议关闭和对端完成业务处理，仍然是需要分别判断的事件。

这次调试把一条 TCP 连接的两种观察方式对应起来：x64dbg 说明程序在什么时刻提交或取走了哪些字节，Wireshark 说明协议栈如何传输、确认和关闭这条字节流。沿着“参数—缓冲区—返回值—报文”的顺序交叉核对，就能从具体证据还原通信过程，并判断一个问题发生在应用协议、API 调用还是 TCP 连接状态上。
