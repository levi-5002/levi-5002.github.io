Windows x64 异常处理之 VCH：从异常分发后段、处理器链、返回值，到 x64dbg 与 ML64 实验

在前面的《Windows 异常处理之 SEH》和《Windows 异常处理之 VEH》中，我们已经知道：异常发生后，Windows 并不是直接结束进程，而是先尝试找到能够处理异常的代码。在常见的 x64 用户态分发路径中，调试器先获得首次异常通知（如果存在调试器），之后才轮到进程级 VEH 和当前线程的栈帧式 SEH。

但是在 x64dbg 中调试 ntdll!RtlDispatchException 时，我们可能看到这样的现象：明明 VEH 已经返回 EXCEPTION_CONTINUE_EXECUTION，系统仍然调用了另一次 RtlpCallVectoredHandlers。 有时第二次调用传入的 R8D=1，与第一次调用的 R8D=0 不同。第二次调用究竟在处理什么？

答案就是本文的主角：VCH（Vectored Continue Handler，向量化继续处理程序）。

一、VCH 是什么：为什么 VEH 和 SEH 之外还有一层？

1. VCH 的定义与地位

VCH 的全名是 Vectored Continue Handler。应用程序通过 AddVectoredContinueHandler 注册一个回调，使其加入当前进程的向量继续处理器列表。与 VEH 一样，VCH 不绑定某一个 __try、函数栈帧或 SCOPE_TABLE_AMD64，也不在专门的“异常线程”中执行；被调用时，通常仍由发生异常的线程运行。

但是 VCH 和 VEH 的职责不一样：

  • VEH：在异常搜索的较早阶段，优先检查并有机会决定是否处理异常。
  • SEH：依据当前线程的受保护作用域、函数表和异常展开元数据寻找语言处理器。
  • VCH：在某些异常分发后段路径得到回调机会，观察或调整异常记录、准备恢复的上下文；自身的回调返回值不能被简单当作“替前面的异常处理器宣布处理成功”。

特别注意：VCH 的名称含有 Continue，不代表“执行了 VCH 就一定继续执行”。 部分异常搜索失败的路径也可能调用 VCH，随后分发器仍返回“无人处理”。因此它不是普通意义的成功恢复通知。

__finally 与 VCH 完全不同：__finally 属于栈帧清理机制，而 VCH 是一个进程级、显式注册的异常回调列表。

二、一张图理解 VCH 的实际调用阶段

这张图是分支关系图，不意味着每种异常都一定经历所有节点。尤其要分清：

  1. VEH 已经请求继续执行：普通 SEH 搜索一般不再需要；VCH 仍可能执行。
  2. SEH 筛选器返回 EXCEPTION_CONTINUE_EXECUTION：可以进入相应的 VCH/恢复路径。
  3. SEH 返回 EXCEPTION_EXECUTE_HANDLER：系统转向目标 __except 处理块及相关栈展开，不是从原故障地址恢复的同一条路径，不能认为一定要先执行 VCH。
  4. 搜索失败：在一些 Windows 逆向观察及 ReactOS x64 兼容实现中，VCH 也可能被调用，但后续依旧不恢复原执行流。
  5. 调试器已在首次机会处理异常：不必进入目标进程的 VEH/SEH/VCH 用户态搜索链。

Windows 的具体异常分发出口及辅助函数名随版本变化；微软公开文档没有承诺上图每个内部跳转作为稳定 ABI。（参见文末参考资料 1、4、7）

3. 生命周期与安全注意事项

  • 如果回调代码在 DLL 中，卸载 DLL 不会自动注销 VCH；之后发生异常，可能调用到已经卸载的代码地址。微软明确提醒需要显式注销。（参见文末参考资料 1）
  • 进程里不同线程的异常都可能触发同一 VCH 回调，回调通常在产生异常的线程内运行，因此共享计数、日志和资源应考虑并发。
  • 不要在回调中做复杂堆分配、持锁、窗口操作、大量 I/O。故障现场本来就可能处在堆、锁或栈不稳定的状态。
  • 注册和注销可能与回调正在执行并发发生。公开 API 只保证接口用途，不保证你自行猜测的内部链表节点布局永久有效。

四、VCH 回调参数：结构体和 x64 寄存器

1. VCH 与 VEH 使用同一种回调类型

不要因为类型名带有 EXCEPTION_HANDLER 就认为只能用于 VEH。 AddVectoredExceptionHandler 与 AddVectoredContinueHandler 都接受这种函数指针。

Windows x64 调用约定下，回调第一个参数放在 RCX，返回的 LONG 放在 EAX：

这套布局与你的 VEH 实验相同，但与 x64 底层 SEH 语言处理器的四参数调用完全不同。

2. EXCEPTION_POINTERS

x64 偏移 字段 指向什么
+0x00 ExceptionRecord 异常原因、异常地址、附加参数
+0x08 ContextRecord 被保存的线程 CPU 上下文

因此，在 x64dbg 的 VCH 回调入口处，[RCX] 不是异常码，而是异常记录指针；还需访问一次 [ [RCX] ] 才能看到开头的 ExceptionCode。

3. EXCEPTION_RECORD

原生 x64 下常见关键偏移如下：

偏移 字段 用途
+0x00 ExceptionCode 例如 0xC000001D（非法指令）
+0x04 ExceptionFlags 可继续/不可继续等标志
+0x08 ExceptionRecord 关联或嵌套异常记录指针
+0x10 ExceptionAddress 发生异常的指令位置
+0x18 NumberParameters 有效附加信息个数
+0x20 ExceptionInformation[0] 附加信息起点

4. CONTEXT 与 RIP

真实程序直接包含 <Windows.h>，不要复制一份不完整的 CONTEXT 结构体重新声明。在 x64 实验中常看的字段是：

CONTEXT 字段 典型 x64 偏移 含义
Rax 0x78 通用寄存器
Rsp 0x98 保存的栈顶
Rip 0xF8 保存的指令指针
EFlags 0x44 保存的处理器标志位

VCH 可以读取 ContextRecord->Rip，在特定路径中也可以改写它。但能够修改结构体和系统之后一定会恢复这个上下文是两个不同判断。特别是在异常根本没有被处理的路径上，随便修改 RIP 不能替代 VEH/SEH 的处理决定。

5.VCH 的返回值

返回值 十六进制 含义 实际效果
EXCEPTION_CONTINUE_SEARCH 0x00000000 继续遍历 继续调用后面的 VCH
EXCEPTION_CONTINUE_EXECUTION 0xFFFFFFFF 结束 VCH 遍历 停止调用后面的 VCH
EXCEPTION_EXECUTE_HANDLER 0x00000001 不适用于 VCH 不是 VCH 约定的有效返回值

VCH 注册与 .pdata/.xdata 的关系

VCH 注册不需要查询某个业务函数的 .pdata 来找到处理器。它靠进程级已注册的回调列表定位。

不过 VCH 回调仍是正常的 x64 函数：如果它建立复杂栈帧，编译器仍需按 x64 ABI 生成适当的展开元数据，供栈回溯和嵌套异常使用。这里要分清回调的登记方式和回调自身如何展开栈。

关键问题 A：VEH 返回 -1，VCH 返回 0，还会恢复吗？

在原异常可继续、上下文合法、VEH 已确定处理成功的前提下，通常仍会恢复。

也就是说，VCH 返回 CONTINUE_SEARCH 不是“撤销 VEH 的处理结果”。

八、VCH 的实际调用条件：六种需要分开的情况

场景 典型 VCH 行为 不能得出的错误结论
① VEH 返回 CONTINUE_EXECUTION 通常在恢复路径中调用 不能说后续一定还要查 SEH
② VEH 放行，SEH 返回 CONTINUE_EXECUTION 可能在该恢复出口调用 不能说 __except 处理块也执行了
③ SEH 选择 EXECUTE_HANDLER 常见路径直接展开到 __except，不经同一 VCH 出口 不能说 VCH 等同 __finally
④ 所有处理器未接管或搜索校验失败 部分实现可调用 VCH，仍可能返回 FALSE 不能说“VCH 被调用 = 故障已恢复”
⑤ 调试器 First-Chance 已处理 可能根本到不了进程的用户态异常链 不能说注册 VCH 就一定观察到 int3
⑥ __fastfail、快速终止等特殊异常 可能绕过常规分发 不能说每一种异常都会执行 VCH

把“VCH 被调用的条件”与“程序最终能够继续执行的条件”分开，是这篇文章最重要的知识点。

停下来的函数 典型返回值 应作何解释
MyVeh EAX=FFFFFFFFh 当前 VEH 请求恢复
MyVch EAX=00000000h 当前 VCH 放行后续 VCH，不是取消恢复
RtlDispatchException AL=1 总体分发已由前面的有效处理结果判定成功

特别注意：在某些构建中，RtlpCallVectoredHandlers 也会把列表回调结果转换成布尔值；即使 VCH 列表调用器返回 0，外层 RtlDispatchException 也不需要把之前的 Handled=TRUE 改成 FALSE。

7. 第六处断点：确认执行恢复

成功分发后，KiUserExceptionDispatcher 可能通过 RtlRestoreContext、RtlGuardRestoreContext、NtContinue 等版本相关路径恢复保存的上下文。

不要把“在调试器单步时看到的下一条停止位置”机械地当成真正恢复的第一条指令。 调试器单步方式、断点位置、TF 标志和异常传递设置都可能影响停止时机。最直接的证据，是在明确的 resume_site 下断点，并确认 g_vehHit 与 g_vchHit。

十二、VCH 与反调试、异常驱动控制流的关系

在逆向分析与 CTF 题目中，VCH 值得关注，主要因为它可以成为另一个观察或修改异常现场的位置。

1. 为什么只看 VEH 容易漏掉逻辑？

例如某程序故意执行 ud2，在 VEH 中跳过非法指令，同时 VCH 检查保存的 RIP 或标志位、设置下一阶段状态。仅仅看到 VEH 返回 -1 就直接把异常指令 NOP 掉，可能会漏掉 VCH 引入的状态变化。

这里的“异常作为控制流工具”既可能用于调试、兼容处理，也可能用于控制流混淆；注册 VCH 本身并不能证明程序恶意。

2. VCH 返回 -1 为什么可能影响观测结果？

若某个 VCH 被注册在列表前端并返回 -1，后续 VCH 可能不会收到同一异常。这意味着不同监测器之间存在回调顺序问题。逆向时要核对：

  • 目标到底注册了多少个 VCH？
  • 哪一个 First 非零，后来是否又有新注册？
  • 第一个 VCH 返回 0 还是 -1？
  • 后续 VCH 是真的未注册，还是被前面的回调提前截断？
  • 整体 RtlDispatchException 最终返回 TRUE 还是 FALSE？

是否调用下一个 VCH与是否恢复线程执行必须分别验证，不能只根据 MyVch 的 EAX 推断所有结果。

3. x64dbg 为什么可能让异常处理程序没有机会执行？

因为调试器 First-Chance 通常发生在目标进程的用户态异常处理器之前。如果调试器自己宣告已经处理异常，目标进程的 VEH/VCH 就可能没有接收到它；如果明确放行，才有机会走进目标程序的处理链。int3、单步、ud2 等都应以具体配置和执行记录为准。（参见文末参考资料 10、11）

十三、VCH 常见错误与正确理解

错误观点 正确理解
VCH 就是第二种 VEH，能独立解决任何异常 VCH 处于不同分发阶段，其返回值不能简单替代 VEH/SEH 的处理决定
VEH 返回 -1 后立即直接到原 RIP，不执行其他回调 某些恢复路径会先调用 VCH
VCH 返回 0 就让异常重新进入 SEH 搜索 VCH 的 0 不会自动撤销前面已确定的有效处理结果
VCH 返回 -1 就保证 RtlDispatchException 返回 TRUE 两者返回协议与责任不同，失败出口可能仍是 FALSE
只要 VCH 被调用，说明异常已处理成功 一些搜索失败的出口也可能调用 VCH
所有 __except 处理结束都执行 VCH 进入 __except 的展开路径不是原上下文恢复的同一出口
VCH 与 __finally 等价 一个是进程级向量回调，一个是语言级栈帧清理
VCH 必须靠 .pdata/.xdata 注册 VCH 注册靠独立列表；函数自身的展开信息是另一回事
回调函数进入时 RCX=EXCEPTION_RECORD* 自定义 VCH 回调入口 RCX=EXCEPTION_POINTERS*
First=1 永远比其他模块优先 后来的前插注册可以改变顺序
0、-1、1 在所有异常函数里意义相同 必须区分回调 LONG、SEH 筛选器、底层语言处理器枚举与分发器布尔值
DLL 卸载会自动清除 VCH 必须显式注销，避免悬空回调
每种异常必定走 VEH/SEH/VCH 调试器处理和快速失败等路径可能绕过常规搜索

十五、结语：真正看懂 VCH，要盯住三个判断

第一，是否走到了 VCH？ 这是一个调用路径问题：观察 RtlDispatchException 在当前异常与当前 Windows 构建中是否到达向量继续处理器的调用出口。

第二，VCH 返回了什么？ 这是一个VCH 列表遍历问题：在常见实现中，返回 0 继续遍历后续 VCH，返回 -1 可能提前终止本次 VCH 列表。它与 VEH 的同名返回值不能简单等价。

第三，异常最终有没有被处理？ 这是一个分发器整体状态问题：需要看最初的 VEH/SEH 处理结果、是否允许恢复、保存的 CONTEXT 是否有效，以及 RtlDispatchException 最终返回 TRUE 还是 FALSE。

因此可以记住一条最核心的判断：

VEH/SEH 的有效处理结果决定异常是否可以恢复；VCH 是分发后段的一组进程级回调机会。VCH 可以观察、调整上下文和影响后续 VCH 的调用，但不能仅凭自己的 -1 返回值把未处理异常宣布为已处理。

结合上一篇 VEH 的 ud2 → MyVeh → CONTEXT.Rip += 2 实验，再加入本文的 MyVch，在 x64dbg 中对照两次 RtlpCallVectoredHandlers 的列表选择值，以及三个层级的 EAX/AL，就能把 VEH、SEH、VCH 在 Windows x64 用户态异常分发中的相互关系串起来。
