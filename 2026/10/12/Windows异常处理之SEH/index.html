Windows x64 异常处理之 SEH：从 CPU 异常、函数表、系统调用链到栈展开与 x64dbg 实验

一、SEH 是什么：异常不等于崩溃

异常（Exception）是 CPU 或软件报告的异常控制流事件。发生异常 ≠ 立即崩溃：系统可以交给处理器检查，决定修复并恢复执行、退出出错作用域，或者继续向外搜索。只有最终无人接管、状态无法恢复或触发特殊终止机制时，进程才可能终止。

__try/__except 是 MSVC 扩展，并不是 Windows 系统调用。x64 下也不是在 GS:[0] 链表里插入一个节点，而是编译器用静态函数表、展开信息和作用域表描述保护关系。

1. SEH、VEH 和顶层过滤器分别是什么

机制 注册/语法 生效范围 主要目的
栈帧式 SEH __try / __except 当前线程活动的受保护作用域 局部处理异常
清理处理 __try / __finally 当前活动受保护作用域 正常离开或展开时执行清理
VEH AddVectoredExceptionHandler 进程级回调列表 在普通栈帧式 SEH 搜索前观察或处理异常
顶层未处理过滤器 SetUnhandledExceptionFilter 进程当前的一份顶层设置 最后阶段的异常诊断/默认处置

普通 SEH 处理成功后不会再因为这次异常自动执行顶层过滤器。这也是本文与上一篇的主要区别。

四、描述异常的基础结构体

1. EXCEPTION_RECORD：到底发生了什么

在标准 x64 对齐下，重要字段偏移为：

偏移 字段 含义
+0x00 ExceptionCode 异常类型
+0x04 ExceptionFlags 不可继续、展开状态等
+0x08 ExceptionRecord 关联/嵌套异常记录指针，不是旧式 SEH 的 Next
+0x10 ExceptionAddress 出错指令地址
+0x18 NumberParameters 有效参数个数
+0x20 ExceptionInformation 异常附加信息

访问冲突 0xC0000005 时，ExceptionInformation[0] 常用于表示 0=读、1=写、8=执行，[1] 才是访问失败的目标内存地址。不要将 ExceptionAddress 和访问的目标地址混为一谈。

EXCEPTION_NONCONTINUABLE 表示当前异常不可直接继续执行。展开相关的 EXCEPTION_UNWINDING、EXCEPTION_EXIT_UNWIND 等标志反映处理阶段；不能把展开标志和 STATUS_UNWIND (0xC0000027) 简单当成一回事。

2. CONTEXT：CPU 异常现场

CONTEXT 是包含 RIP/RSP/RAX/RCX/.../EFlags、调试寄存器和浮点/SIMD 状态的较大结构，不建议自己手写整个定义，实际应使用 Windows SDK 的 CONTEXT。

常见原生 x64 布局：

字段 偏移 用途
Rax 0x78 通用寄存器
Rsp 0x98 当前线程的栈指针
Rip 0xF8 要恢复执行的指令地址

处理器可以读取或在符合恢复规则时修改 ContextRecord->Rip。例如 ud2 长度为 2 字节，修改 RIP += 2 并请求继续执行，就可能转到后一条指令。这不意味着所有非法指令都能简单地加 2；指令边界、栈和寄存器状态必须正确。

5. SCOPE_TABLE_AMD64：C 语言哪些代码受哪一个异常处理作用域保护

对于使用常见 MSVC C SEH 语言处理器的函数，UNWIND_INFO 的 ExceptionHandler RVA 可能指向 __C_specific_handler，而紧随其后的 语言专用数据 可解释为 SCOPE_TABLE_AMD64。

它不是一个必须存在的独立 PE 节，也不是任何 UNWIND_INFO 都必须携带的结构。 自定义 MASM 底层处理器、C++ 异常处理器以及部分 /GS 包装处理器可能使用不同格式。

5.1 结构定义与偏移

偏移 字段 说明
+0x00 Count 有多少个作用域记录
+0x04 ScopeRecord[0].BeginAddress 第一条保护范围开始
+0x08 ScopeRecord[0].EndAddress 第一条保护范围结束（开区间上界）
+0x0C ScopeRecord[0].HandlerAddress 过滤器、终止处理器或特殊值
+0x10 ScopeRecord[0].JumpTarget except 处理块入口，或 0(__finally)
+0x14 ScopeRecord[1].BeginAddress 第二条记录起始；每条占 0x10 字节

HandlerAddress 的常见意义：当 JumpTarget != 0 时属于异常过滤/处理作用域，HandlerAddress 通常指向 Filter；常量 1 可作为无须调用单独函数的 EXCEPTION_EXECUTE_HANDLER。当 JumpTarget == 0 时，典型 C SEH 表示终止处理器（__finally），HandlerAddress 指向清理函数。具体仍以当前语言处理器实现为准。

5. GS、TEB 与 x64 SEH 的关系

在原生 Windows x64 用户态，GS 通常关联当前线程的 TEB。常见布局中，GS:[30h] 可以取得 TEB 的自指针，GS:[60h] 可取得 PEB 指针。但这不意味着 GS:[0] 是 x86 旧式 SEH 链头：原生 x64 的常规栈帧式 SEH 依赖 .pdata/.xdata 函数表及活动调用栈。TEB/PEB 的具体内部字段和偏移还应以目标系统版本为准。

输入为当前检查的指令地址；输出为函数表项及模块基址。查不到不必然代表恶意代码，可能是符合约定的叶函数。这个函数只查找展开信息，不决定“SEH 是否接受异常”。

4. RtlVirtualUnwind：计算上一层，不真正 ret

x64 形式：

  • HandlerType：查询异常处理器（UNW_FLAG_EHANDLER）、终止处理器（UNW_FLAG_UHANDLER）或不查询处理器。
  • FunctionEntry、ImageBase：定位展开信息。
  • ContextRecord：输入/输出，被计算成上一调用者的上下文。
  • 返回值：可能得到此帧的底层语言处理器指针。
  • HandlerData：接收其语言专属附加数据（若存在）。
  • EstablisherFrame：对应的建立者栈帧。

例如被调用函数序言为 push rbx; sub rsp,20h，虚拟展开可以模拟撤销栈空间分配、恢复保存的 RBX，并从返回地址计算调用者的 RIP/RSP。它没有让 CPU 在出错函数内真实执行 ret。

5. RtlpExecuteHandlerForException → __C_specific_handler

在一些 Windows 构建中，RtlDispatchException 通过 RtlpExecuteHandlerForException 一类内部包装器间接调用语言处理器；也可能经过 CFG 间接调用跳板。这些包装器/跳板不是新注册的 SEH，也不是固定公开 ABI。

6. RtlUnwindEx：选择了 __except 后才真正退出作用域

  • TargetFrame：展开目标栈帧；为 NULL 可以表示退出式展开。
  • TargetIp：目标继续执行地址。
  • ReturnValue：恢复时放入整数返回寄存器的值。
  • ContextRecord：展开所需上下文。

与虚拟展开不同，真实展开会在需要退出的作用域上执行相应清理（如 __finally），并将执行流导向选择的 __except。它不是“把栈字节清零”，也不是逐层正常运行所有 ret。

七、四种典型结果，对应四条不同的调用链

情况 A：局部 SEH 处理异常（最重要）

RtlVirtualUnwind 不是在每个程序里都必须出现同样次数；这是帮助识别系统职责的概念调用链。真正选择处理器后，目标处理块不需要再经由顶层未处理过滤器。

情况 B：内层不处理，外层处理

顺序是：Inner 的筛选器 0 → 沿当前线程的调用栈继续向外 → Outer 筛选器 1 → 真实展开 → Outer.__except。不是 Inner.__except 执行后再执行 Outer.__except。

情况 C：修改 CONTEXT 后直接继续执行

此时通常不需要为了转入 __except 而展开到外层处理作用域。如果没有修复根本故障，恢复后可能反复触发同一异常。

十三、常见误区与排错

误区 正确理解
x64 SEH 必须修改 GS:[0] 原生 x64 主要采用函数表式 SEH；GS 关联 TEB，不等于 x86 异常注册链
.pdata 里直接存放 __except 代码 .pdata 主要是函数表，语言处理器和作用域信息经 .xdata 等关联
RtlVirtualUnwind 会真实执行调用者的 ret 它只计算调用者 CONTEXT，不执行正常函数返回
RtlLookupFunctionEntry 查到函数就等于能处理异常 能否处理还要看 UNWIND_INFO 的语言处理器、具体有效的作用域及过滤结果
筛选器返回 1 与底层处理器返回 1 等价 前者执行 __except，后者继续搜索
搜索过 FuncB 就已经执行了它的 finally 过滤搜索与真实展开是两个阶段
外层 __except 总会先于内层 finally 常见次序是 Filter → finally → except
两线程同一 RIP 就只会调用同一 SEH 处理器选择还依赖各线程独立的活动栈帧和作用域
局部 SEH 完成后必然进入 UnhandledExceptionFilter 已处理就不必进入顶层未处理路径
调试器拦截异常说明程序立即崩溃 First Chance 只表示调试器首先获得处理机会
每次都能在 ntdll 里找到同名 Rtlp... 函数 内部函数名、跳板与调用链随系统版本变化
RaiseFailFastException 必然经过普通 SEH 快速失败可绕过普通的帧式/向量异常处理并终止进程

十四、结语

真正理解 Windows x64 SEH，必须把三件事串在一起：

第一，异常记录和执行现场： EXCEPTION_RECORD 描述异常本身，CONTEXT 保存故障线程的 CPU 状态。

第二，处理器查找： RtlDispatchException 从当前线程活动栈帧出发，结合 RtlLookupFunctionEntry、RtlVirtualUnwind、.pdata/.xdata 和语言处理器定位有效的保护作用域。

第三，确定处理后的控制转移： 过滤器要么继续搜索，要么要求恢复 CONTEXT，要么选择处理块并经过 RtlUnwindEx 等机制实际展开，最终进入对应的 __except。顶层过滤器只是“局部异常最终没有得到处理”时可能到达的另一层机制。

逆向时不要只盯着哪一个 API 被调用，更要看：当前异常是哪一个线程的、ControlPc 落在哪个受保护作用域、HandlerData 指向什么、返回值属于哪一套协议、以及是否已经从搜索阶段进入真正的展开阶段。
