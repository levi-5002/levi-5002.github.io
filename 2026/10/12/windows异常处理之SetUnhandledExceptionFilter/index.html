Windows 异常处理机制详解：SetUnhandledExceptionFilter 从内核异常分发到程序终止与x64dbg手动实验

一、Windows 异常处理机制与核心原理

1. 异常与程序崩溃

异常（Exception）是程序执行过程中需要特殊处理的事件，既可以由 CPU 硬件产生，也可以由软件主动产生。

例如：

由于 EAX=0，第二条指令尝试向无效地址写入数据，通常触发访问违规异常 0xC0000005。

但是，异常发生并不代表进程立即终止。

Windows 可以保存故障线程的寄存器状态，寻找合适的异常处理程序。如果异常得到处理，线程可能恢复执行、重新执行故障指令，或者转移到异常处理代码。

需要特别区分：

概念 含义
Exception 程序或 CPU 产生了异常条件
Handled Exception 异常已经由某个处理程序接管
Unhandled Exception 异常没有被相应处理机制解决
Crash 程序因无法恢复的错误或致命条件而终止

如果异常发生后，问题没有解决，却直接恢复相同的指令，通常还会再次产生异常。

但程序不一定非要修复原始指令，也可以在异常处理后跳转至其他合理的执行位置。

2. 异常从 CPU 到用户态的分发过程

Windows 普通应用程序主要运行在 Ring 3（用户模式），内核代码运行在 Ring 0（内核模式）。

当 CPU 执行一条发生硬件异常的指令时，例如无效内存访问，CPU 会通过异常向量转移到对应的内核入口。

其中有几个关键函数。

1. KiDispatchException

这是 Windows 内核异常处理实现中常见的内部函数名称之一。它参与异常分发、调试器通知以及决定是否需要向用户态分发等过程。

它属于系统内部实现，不是开发普通 Win32 程序时应直接调用的公开 API。

2. KiUserExceptionDispatcher

这是 ntdll.dll 中典型的用户态异常分发入口。

当 Windows 决定将异常交给用户模式处理时，可以使用户线程进入相应的异常分发逻辑。

它会使用异常记录和保存的线程上下文继续分发。

3. RtlDispatchException

它负责在用户态分发向量化异常处理器（VEH），并沿当前线程的栈帧搜索与语言有关的结构化异常处理器（SEH）。它本身不会无条件直接调用 SetUnhandledExceptionFilter 所设置的函数：本次实验中是搜索进入系统线程启动函数的异常过滤表达式，才进一步进入 UnhandledExceptionFilter。

如果异常被处理，Windows 可以根据处理结果恢复执行。

如果当前搜索没有找到处理办法，异常会继续进入未处理异常路径；存在调试器时还可能进入 Second Chance。

4. NtContinue / NtRaiseException

在典型的 Windows 异常实现中，恢复线程上下文和继续报告未处理异常会涉及这些底层接口。

要注意：恢复执行不等于简单执行当前回调的下一条汇编指令。操作系统需要恢复原故障线程的上下文。

调试器的 First Chance 与 Second Chance

Windows 在调试状态下，会先通过调试事件通知调试器。这里的“异常通知”并不等同于“应用代码一定会收到异常”：调试器可以选择将异常吞掉，也可以交还被调试程序处理。

  • First Chance：在应用程序自己的异常处理程序运行前，先给调试器处理机会。
  • Second Chance：异常没有被程序处理时，调试器可以获得最后一次处理机会。

调试器可以通过 ContinueDebugEvent 提交：

前者表示调试器已经处理该异常，后者表示交由后续异常机制继续处理。

因此，在 x32dbg 或 x64dbg 中看见访问违规提示，不能直接认定进程已经崩溃。

3. VEH、SEH 与顶层未处理异常筛选器

Windows 的异常处理不是只有一个回调列表。

机制 注册方式 核心特点
SEH __try / __except 与当前线程的栈帧及异常处理范围相关
VEH AddVectoredExceptionHandler 进程范围内注册多个向量化异常处理函数
UEF SetUnhandledExceptionFilter 设置进程当前的顶层未处理异常筛选器

传统 Windows x86 SEH 可以通过 FS:[0] 查找异常注册链表头；而在 x64 中，主要通过 .pdata、.xdata 及展开信息查找异常处理程序。

不过：

SetUnhandledExceptionFilter 并不是向 x86 的 FS:[0] 异常链表中加入节点。

它设置的是进程范围内的顶层未处理异常筛选回调。

4. Windows x64 的表驱动 SEH：为什么需要 .pdata 与 .xdata？

4.1 x86 链表式 SEH 与 x64 表驱动 SEH 的区别

在传统的 32 位 Windows 用户态代码中，可以从线程相关的 FS:[0] 入口找到 SEH 注册记录链。每个活动记录通常关联相应的栈帧和异常处理器。

但在 Windows x64 中，正常的栈帧式 SEH 主要依赖 PE 映像中的异常目录和展开元数据，而不是沿着 FS:[0] 遍历链表。调试时看到 GS:[60h] 获取 PEB，也不代表正在读取 x86 风格的 SEH 链表：PEB 与栈帧的异常展开元数据是两件不同的事。

对比项目 x86（经典 Win32 SEH） x64（主流原生代码）
搜索入口 每线程的 SEH 注册链 当前 RIP、函数表和展开信息
注册信息 栈上的异常注册记录 映像函数表以及语言相关处理信息
主要依赖 FS:[0] 等线程状态 .pdata / .xdata、RUNTIME_FUNCTION、UNWIND_INFO
调用栈向外搜索 链表中查找后继记录 对保存的 CONTEXT 进行逐帧虚拟展开
ASLR 影响 处理器绝对地址可能变化 函数表包含相对映像基址的 RVA，运行时加上映像基址

4.2 .pdata、RUNTIME_FUNCTION 和 .xdata 的关系

对需要栈展开信息的 x64 函数，链接器通常在 .pdata 中生成 RUNTIME_FUNCTION 项。这些条目描述函数的起止范围，以及相应的展开信息位置；进一步指向 .xdata 中的 UNWIND_INFO。

UNW_FLAG_EHANDLER 表示有异常处理器可供异常搜索阶段检查；UNW_FLAG_UHANDLER 涉及栈展开时的终止/清理处理。有可展开信息并不代表这个函数一定定义了 __except。 只有对应元数据指明了语言处理器，才有相应的处理器可调用。

有些简单叶子函数没有独立的函数表项，可以按约定模拟一次返回地址恢复；动态生成的代码则可能需要通过运行时函数表注册 API 提供展开信息。因此，不能把“.pdata 没有该函数”直接等同于“这是恶意代码”。

4.3 RtlLookupFunctionEntry 与 RtlVirtualUnwind 各做什么？

名称 核心工作 调试时应关注的输出
RtlLookupFunctionEntry 根据当前控制地址定位对应的运行时函数表项 映像基址、RUNTIME_FUNCTION 指针
RtlVirtualUnwind（实际实现中可能见到内部变体） 利用展开元数据，推算调用者的 RIP、RSP 等上下文 更新后的 CONTEXT、EstablisherFrame、语言处理器和处理器数据
DISPATCHER_CONTEXT 保存异常分发器正在检查的帧与相关状态 ControlPc、函数表项、语言处理器、作用域数据

本实验跟踪中出现的 RtlpxVirtualUnwind 属于系统内部实现细节；理解它的功能时可以对照公开文档中的 RtlVirtualUnwind。内部函数名、寄存器和具体指令不能保证不同 Windows 版本完全一致。

5. 从 RtlDispatchException 到 __C_specific_handler：谁真正判断异常？

理解 x64 SEH 时，必须把 异常分发器、语言异常处理器 和 过滤表达式 分开。

层次 本次调试中的代表函数 负责的事情
异常分发入口 KiUserExceptionDispatcher 接收用户态异常现场，发起搜索并安排后续路径
异常搜索与调度 RtlDispatchException 检查 VEH，并逐个栈帧查找可调用的异常处理器
处理器调用包装 RtlpExecuteHandlerForException 以异常分发要求的方式调用找到的语言处理器
语言异常处理器 __C_specific_handler 解释当前函数的 C SEH 作用域表及过滤表达式
SEH 过滤函数 例如 RtlUserThreadStart$filt$0 计算 __except 过滤表达式的结果
顶层未处理异常机制 UnhandledExceptionFilter 处理进入顶层的未处理异常，并在适用条件下调用应用设置的筛选器
用户回调 MyException 读取异常现场并返回 LONG 筛选结果

RtlDispatchException 搜索到某帧的 UNW_FLAG_EHANDLER，并不意味着已经找到了 MyException；它先找到的是该栈帧的语言处理器。例如，本次线程入口帧关联的是 __C_specific_handler。

随后，__C_specific_handler 依据该函数的作用域信息判断：异常发生的控制地址是否处在受保护范围内、需要评估哪个过滤表达式、若选择处理应转到哪个处理块。它不是简单地把所有回调按注册顺序遍历一遍。

6. 为什么异常会查找到 RtlUserThreadStart？它是不是新线程？

本次 x64dbg 的虚拟展开路线是：

RtlUserThreadStart 属于 Windows 的线程启动路径。它通常早于用户线程入口函数执行，外层可以存在系统提供的异常保护。看到这个函数，不代表异常发生时 Windows 临时创建了新线程。 这是对同一个故障线程先前的调用路径进行回溯。

相反，KiUserExceptionDispatcher 出现在异常分发阶段，并不是 main 主动执行 call KiUserExceptionDispatcher。当系统把异常转交用户态时，会安排故障线程进入异常分发入口；这是异常执行路径的转移，而非普通业务函数调用，也不需要创建新线程。

本次观察到的 RtlUserThreadStart$filt$0 是线程启动函数的一段过滤表达式辅助代码。为了理解，可以把它抽象成“线程入口外围存在某种 __try / __except 保护，过滤表达式进一步执行顶层未处理异常机制”。这只是对本次二进制实现的概念解释，不是 Microsoft 公开保证的逐行源代码。 CRT 初始化方式、Windows 版本、调试状态和线程启动路径不同，实际堆栈可能存在差异。

SetUnhandledExceptionFilter 设置的是进程层面的顶层筛选函数，但回调 在触发异常的那个线程中执行。因此，一个进程的不同线程可能共用同一个设置，局部 __try / __except 的保护范围仍要按照每个线程自己的栈帧分别搜索；一个线程的 SEH 不能自然地“跳过去”捕获另一个线程的异常。

7. 虚拟展开与真实栈展开：搜索阶段为什么还没有执行 __except？

虚拟展开（Virtual Unwind） 是在异常搜索阶段利用 UNWIND_INFO 推算上一层调用帧的寄存器和栈指针，回答“下一层调用者在哪里”。它不等于已经在真实 CPU 栈上执行了函数返回，也不直接运行所经过每一层的 __finally。

真实栈展开（Actual Unwind） 则是在选定异常处理目标后，处理不再保留的调用帧，运行适用的清理/终止处理程序，并构建转入目标异常处理块所需的执行状态。常见实现会涉及 RtlUnwindEx 以及恢复目标上下文的 RtlRestoreContext。

阶段 要解决的问题 本次可见函数 是否已转入 __except
搜索 哪个栈帧有适用的异常处理规则？ RtlDispatchException、RtlLookupFunctionEntry、RtlpxVirtualUnwind 否
过滤 当前 SEH 规则愿意处理这个异常吗？ __C_specific_handler、过滤表达式、MyException 尚未进入处理块
实际展开 离开故障位置，清理经过的帧，转向处理目标 RtlUnwindEx 准备转入
上下文恢复 让 CPU 从目标处理块对应的状态继续 RtlRestoreContext 等 即将进入/已经进入
最终执行 运行选定的处理代码 线程入口的 __except 分支 是

注意两种“恢复”完全不同：过滤器返回 EXCEPTION_CONTINUE_EXECUTION 时，系统尝试从故障点或修改后的异常 CONTEXT 继续；而过滤器选择 EXCEPTION_EXECUTE_HANDLER 后，系统会转入匹配的 __except，并不是回去重新执行出错指令。

在本次跟踪中，实际路径表现为：MyException 返回 1 → 线程入口过滤表达式选择执行处理块 → RtlUnwindEx → RtlRestoreContext → RtlUserThreadStart 的 __except 分支 → NtTerminateProcess。因此，不是 MyException 直接调用了终止进程 API；它的返回值参与了外层异常处理规则的选择。

4. 已注册回调的保存、指针编码与跳板函数

SetUnhandledExceptionFilter 的公开语义是“把当前进程的顶层筛选函数改为指定函数，并返回旧函数指针”。至于系统在内部如何保存该指针，是实现细节。

在本文记录的这次 Windows 跟踪中，系统使用了类似 KERNELBASE!BasepCurrentTopLevelFilter 的内部全局状态，并通过指针编码/解码路径保护所保存的地址。x64dbg 中最初传入的地址也可能是模块跳板（thunk），跳转后才到真正的 MyException 函数体。不要把“汇编里看到的第一次地址”与“回调主体起始地址”混为一谈。

这说明两件事：第一，内部编码并不改变“进程只有一个当前设置”的 API 语义；第二，内部变量名、编码过程和 thunk 形态都不是可移植的公开 ABI 约定，不同系统或构建版本应以实际调试证据为准。

5. NULL 返回值不等于注册失败

特别需要纠正一个常见误区：SetUnhandledExceptionFilter 返回的是“旧的顶层筛选器地址”，返回 NULL 仅表示先前没有设置过这样的顶层筛选器，不能据此判定新回调注册失败。

6. 为何调试器中注册了回调却可能不进入？

官方文档对 SetUnhandledExceptionFilter 的顶层回调调用条件限定了进程未被调试。在被 x64dbg 附加或启动的情况下，即使调试器把 First Chance 异常交还给程序，也不能推导出 MyException 必定会执行；实际还取决于运行时和系统顶层过滤路径。详见第三部分的实验记录与本节第 15 小节。

12. 异常返回值：LONG 与 EXCEPTION_DISPOSITION 不能混淆

返回值 顶层未处理异常筛选器中的意义
EXCEPTION_CONTINUE_SEARCH 继续 UnhandledExceptionFilter 的默认处理逻辑
EXCEPTION_EXECUTE_HANDLER 返回到关联的最终异常处理程序，通常导致进程终止
EXCEPTION_CONTINUE_EXECUTION 尝试根据保存或修改后的线程上下文继续执行

这里有两个容易混淆的地方。

第一，顶层筛选器返回 EXCEPTION_CONTINUE_SEARCH，不表示自动调用前一个通过 SetUnhandledExceptionFilter 注册的函数。

第二，EXCEPTION_EXECUTE_HANDLER 在普通 SEH 的 __except 表达式中意味着进入对应异常处理块，而在顶层未处理异常阶段通常意味着进入最终处理或终止路径。

1. 过滤表达式返回 LONG：-1 / 0 / 1

__except 的过滤表达式，以及用户注册的 MyException，使用的是异常筛选结果约定：

数值 常量 筛选层含义
-1 EXCEPTION_CONTINUE_EXECUTION 要求从保存或修改过的异常上下文继续执行
0 EXCEPTION_CONTINUE_SEARCH 本层不接受异常，交给其他处理逻辑
1 EXCEPTION_EXECUTE_HANDLER 选择当前受保护范围关联的异常处理块

对于顶层 SetUnhandledExceptionFilter 回调，0 还需按 UnhandledExceptionFilter 自身的公开契约理解：它让系统继续其默认的顶层未处理异常逻辑，并非自动恢复上一个被替换的回调。

2. 语言异常处理器返回 EXCEPTION_DISPOSITION：0 / 1 / 2 / 3

底层语言处理器（例如 __C_specific_handler）返回给异常分发器的枚举是另一套协议：

数值 EXCEPTION_DISPOSITION 枚举项 含义
0 ExceptionContinueExecution 已决定可继续恢复异常执行
1 ExceptionContinueSearch 当前栈帧未接受，继续查找更外层帧
2 ExceptionNestedException 协调嵌套异常时的分发状态
3 ExceptionCollidedUnwind 协调栈展开过程中碰撞的展开情况

不要因为两者都出现了数字 0 和 1，就把它们当作同一种返回值。 一套是应用级过滤表达式的决策，另一套是语言处理器向分发器报告的处理结果。

3. 两套返回值如何联系？

  • 过滤器给出 -1：若允许继续，语言处理器可向分发器报告 ExceptionContinueExecution（底层数值 0）。
  • 过滤器给出 0：继续检查其他适用的作用域；若都不接受，则向外层栈帧继续搜索，报告 ExceptionContinueSearch（底层数值 1）。
  • 过滤器给出 1：已选择相应 __except，语言处理器可能调用 RtlUnwindEx，转入实际展开和处理代码，不一定按普通函数返回路径回到分发器。

在本次 demo 中，MyException 通过 mov eax, EXCEPTION_EXECUTE_HANDLER 返回的 1，属于过滤层的 1，并不是 __C_specific_handler 的 ExceptionContinueSearch。

14. 异常未处理时的结果与进程终止

当异常不能安全恢复时，Windows 通常会进入默认未处理异常流程，可能包括错误报告、转储生成和进程终止。

Windows Error Reporting（WER）可以根据系统配置收集崩溃数据。

但是必须区分：

  • SetUnhandledExceptionFilter：注册顶层异常筛选回调。
  • MiniDumpWriteDump：生成调试转储文件。
  • WER：Windows 的错误报告机制。

它们不是同一个功能，更不能认为每次异常发生后都会向网络上传信息。

生产软件中，顶层回调应主要用于最后的故障诊断。已经出现栈损坏、堆损坏或严重状态破坏时，不应盲目依靠 EXCEPTION_CONTINUE_EXECUTION 强行恢复程序。

特别是 RaiseFailFastException、__fastfail 等机制，可能绕过常规异常处理并快速终止进程。

erun 与 serun 的实际区别

根据 x64dbg 的命令文档，erun / ego 会把 First Chance 异常交给被调试程序；serun / sego 则会吞掉当前异常，跳过将它分发给被调试程序的步骤。

吞掉异常不等于修复异常原因。 如果故障 RIP 仍然指向对零地址写入的指令，执行继续之后通常又会产生同样的访问违规。反过来，erun 只是允许应用程序的异常机制介入，不能保证调试状态下 SetUnhandledExceptionFilter 的用户回调必然会运行。

2. 为什么 x64dbg 中可能无法进入回调？

因为 SetUnhandledExceptionFilter 的正常回调调用条件包含进程未被调试。

用 x64dbg 启动程序时，调试器会先接到异常事件；即使选择不处理首次机会异常，也不能保证顶层筛选器会像未调试时一样执行。

建议首先直接运行 EXE，确认注册与恢复行为，然后再用调试器观察访问违规的位置、异常代码以及寄存器值。

3. 常见问题总结

为什么会重复进入异常回调？

通常是返回了 EXCEPTION_CONTINUE_EXECUTION，但导致异常的条件并未真正消除。

为什么之前注册的回调不再执行？

可能是调用了新的 SetUnhandledExceptionFilter，替换了之前的设置。

为什么修改了回调内部的 EAX，却没有修复原程序？

因为回调运行时的 EAX 与保存于 CONTEXT 的 EAX 是两个概念。要修改的是用于恢复故障线程的寄存器上下文。

为什么有些崩溃没有进入回调？

可能是异常已被其他处理程序接管、进程被调试、发生快速失败、栈已损坏，或程序根本没有走到顶层处理路径。

结语

Windows 异常处理的重点不是“程序报错后立即结束”，而是操作系统提供了一套从异常检测、保存上下文、处理程序查找，到恢复执行和最终崩溃收尾的机制。

SetUnhandledExceptionFilter 位于其中的顶层未处理异常阶段。开发者可以利用它检查异常原因、读取异常现场，或者在非常明确的条件下修改保存的上下文尝试恢复执行。

学习它时，最重要的是理解三者的关系：

EXCEPTION_RECORD 描述发生了什么错误；CONTEXT 保存发生错误时的寄存器现场；筛选回调的返回值决定 Windows 下一步应该怎样处理。

对于逆向分析而言，理解这三者，就能够进一步分析通过异常改变控制流的 CTF 程序，以及 Windows 调试器中的异常分发行为。
