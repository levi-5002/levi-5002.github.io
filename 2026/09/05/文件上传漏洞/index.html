文件上传漏洞：从原理到实战

一、什么是文件上传漏洞

文件上传功能本身并不是漏洞。头像、附件、图片、压缩包、文档上传都是非常常见的业务功能。

真正的文件上传漏洞（File Upload Vulnerability），通常指服务端对用户上传文件的文件名、扩展名、MIME、文件内容、保存路径、服务器解析行为或后续处理流程缺乏有效限制，导致攻击者能够让服务器保存本不应该保存的文件，甚至让上传内容被 Web 服务器或脚本解释器执行。

最严重的情况是：

但要特别注意：“上传成功”不等于“漏洞利用成功”，更不等于“已经获得代码执行”。

例如，一个带 PHP 代码的 1.jpg 能够成功上传，只能证明服务器允许这个文件存在。若 Web 服务器仍然把它当普通 JPEG 返回，那么 PHP 代码不会自动执行。

因此，文件上传漏洞应当拆成几个不同层次来看。

1.1 文件上传漏洞常见于哪些业务位置

实际渗透测试中，凡是出现“用户向服务端提交文件”的位置，都值得进入上传安全检查清单。常见入口包括：

  • 用户注册、个人资料、头像修改；
  • 身份认证材料，例如证件照片、银行卡图片、资质文件；
  • 商品、订单、评价中的图片或视频附件；
  • 工单、客服、邮件、IM、论坛、朋友圈/空间等附件功能；
  • 后台 CMS、OA、富文本编辑器、文件管理器中的上传组件；
  • 数据导入功能，例如 CSV、Excel、ZIP、模板包、插件包；
  • 主题、插件、安装包、备份包上传；
  • API 中的 multipart 文件接口；
  • 对象存储直传、分片上传、云盘同步等现代上传链路。

这里要避免一个常见误区：“存在上传按钮”只是说明存在攻击面，并不等于存在上传漏洞。

真正需要继续确认的是：服务端是否允许攻击者控制文件内容、文件名、后缀、保存路径或后续解析行为。

攻击者至少能够控制以下一项：

  • 文件内容；

  • Content-Type / Content-Disposition 是否可控；
  • 是否允许上传 HTML/SVG 等主动内容并在同源域名展示；
  • AccessKey / SecretKey 是否泄露在源码、前端 JS、日志、CI 配置中；
  • 上传后的对象是否会被后台任务再次解析、解压或导入。

所以“使用云存储”是一种隔离措施，而不是替代所有上传校验。
